# 데이터 안전성 후속 조치 (코드 리뷰 우선순위 표 마무리)

배경: `docs/map-image-indexeddb.md`로 이어진 코드 리뷰 후속 작업의 우선순위 표(높음 3건, 중간 3건, 낮음 1건) 중 나머지 항목을 처리한 기록입니다. 각 항목을 실제 코드에서 다시 확인한 뒤 진행했고, 리뷰에서 지적된 그대로가 아니라 실제로 확인된 내용 기준으로 정리합니다.

## 처리한 것

### 저장 디바운스 (중간 → 완료)
`saveData()`가 입력 하나(타이핑 등)마다 전체 상태를 `JSON.stringify`해서 동기 저장하던 것을 400ms 디바운스로 바꿨습니다. `_flushSaveData()`가 실제 쓰기를 담당하고, `saveData()`는 이제 쓰기를 예약만 합니다. 데이터 유실을 막기 위해 **탭을 닫거나 페이지를 이동할 때(`beforeunload`)**, **백그라운드로 전환될 때(`visibilitychange: hidden`)** 대기 중인 변경을 즉시 flush합니다. `saveData()`의 반환값을 실제로 쓰는 호출부가 없어서(전수 조사 확인) 반환 시맨틱을 바꿔도 안전했습니다. 회귀 테스트 중 "저장 직후 새로고침해서 값이 남아있는지" 확인하는 테스트들(`test_field_templates.js`, `test_relationship.js` 등)이 `beforeunload` flush가 제때 도는지까지 검증해 줬고, 전체 46개 파일 모두 통과했습니다.

### 백업 세부 스키마 검증 (높음 → 완료)
기존엔 `normalizeData`/`isValidBackupData`가 "각 컬렉션이 배열인가"까지만 확인했습니다. 이 앱 전체에서 `.find(d => d.id === ...)` / `.filter(...)` 식으로 각 항목에 `id`가 있다고 가정하는 코드가 수백 곳이라, 배열 안에 `id` 없는 항목(문자열, `null`, `id` 없는 객체 등)이 섞여 있으면 그 즉시가 아니라 나중에 엉뚱한 화면에서 크래시로 튀어나올 수 있었습니다. `isValidCollectionItem(key, item)`을 추가해 컬렉션별로 형태를 검사하고(`recentColors`만 순수 문자열, 나머지는 `{id: string, ...}`), **형태가 이상한 항목만 걸러내고 나머지는 살리는** 방식으로 `normalizeData`를 확장했습니다. 가져오기(`importDataFile`)도 이제 자체 판별 로직 대신 이 함수를 재사용하도록 바꿔서, 부팅 시 복구와 백업 가져오기가 같은 안전장치를 공유합니다 — 일부 항목만 깨진 백업이라도 전체를 거부하지 않고 정상 항목은 살립니다(가져오기 확인창에 "일부 항목은 제외하고 불러옵니다" 안내 추가).

## 확인했지만 이미 괜찮았던 것

### 백업/복원의 recentColors 일관성 (중간 → 이미 해결돼 있었음)
리뷰가 지적한 시점엔 `recentColors`가 백업 내보내기/가져오기에서 빠져 있었지만, Codex의 1단계 작업(`2e4d02e`, 이 세션에서 병합 확인)에서 `DATA_COLLECTIONS`에 `recentColors`가 포함되며 이미 내보내기·가져오기 양쪽에 들어가 있었습니다. 추가 조치 불필요.

## 조사했지만 일부러 손대지 않은 것

### 테마 저장 실패 무음 (낮음 → 의도적으로 보류)
리뷰가 지적한 `saveTheme()`의 빈 `catch (e) {}`는 메인 앱의 테마 엔진이 아니라, **내보내기 전용 "설정집.html" 뷰어**(`ASSET_CLIENT_JS` 템플릿 문자열 안, 13552행)에 들어 있는 별도의 작은 라이트/다크 토글입니다. 읽기 전용으로 배포되는 독립 HTML 파일의 UI 취향(라이트/다크) 하나가 저장 안 돼도 다음 방문 때 시스템 기본값으로 돌아갈 뿐, 실제 창작 데이터 손실과는 무관합니다. `saveData()`(창작 데이터, 높음)와 같은 수준의 알림 UI를 여기에 넣는 건 위험 대비 되돌아오는 가치가 작아 보류했습니다. 필요하면 나중에 가볍게(알림 없이 그냥 재시도 정도) 처리 가능합니다.

### 전역 키보드 핸들러 충돌 (중간 → 조사 후 보류, 새 발견 있음)
실제로 세어보니 `window.onkeydown = ...`로 직접 대입하는 곳은 **관계도 그래프 페이지**(9560행)와 **지도 페이지**(11694행) 딱 2곳뿐이었고, 다른 두 곳(13187, 13241행)은 페이지를 떠날 때 `null`로 정리하는 코드였습니다. 이 앱은 한 번에 한 페이지만 `#main`에 보이는 구조라, 프로퍼티 대입 방식이 "지금 활성 페이지가 소유권을 갖는다"는 의미로는 실제로 오작동하지 않고 있었습니다 — `addEventListener` 기반으로 바꾸는 게 정석이지만, 지금 당장 깨진 버그는 아닙니다.

다만 조사 중에 **관계도 그래프 페이지의 `mousemove`/`mouseup` 창 이벤트 리스너에는 정리(cleanup) 로직이 아예 없다는 걸 발견했습니다**(9540~9558행 부근). 지도 페이지는 `_mapWinHandlers`로 페이지에 들어갈 때마다 이전 리스너를 명시적으로 제거하는데, 관계도 그래프 페이지는 그 패턴이 없어서 **같은 세션에서 관계도 페이지를 여러 번 열면 리스너가 계속 쌓입니다**(메모리 누수 + 매 마우스 이동마다 중복 실행). 이건 리뷰의 원래 지적(키보드 핸들러)과는 다른, 이번에 새로 발견한 문제입니다. `_mapWinHandlers`와 같은 패턴(등록 전 이전 리스너 제거)을 관계도 페이지에도 적용하면 해결되는데, 세션 시간상 지금 급하게 손대기보다 다음 세션에서 차분히 고치는 걸 권합니다 — 아래 핸드오프 문서에 정리했습니다.
