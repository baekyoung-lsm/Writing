# 지도 배경 이미지를 IndexedDB로 분리 (localStorage 용량 위험 완화)

이 문서는 지도(Map) 배경 이미지(업로드 원본 + 자동 선 감지 결과)의 저장 위치를 `localStorage`(지도 데이터에 Base64로 직접 내장)에서 별도의 IndexedDB 자산 저장소로 옮긴 작업을 정리합니다. 배경: 코드 리뷰에서 "지도 이미지가 저장 용량을 급격히 소모한다"는 지적(원본 + 추적 이미지를 Base64로 지도 데이터 자체에 저장하고, 회차(버전)를 추가할 때마다 그 큰 문자열이 다시 통째로 복제됨)이 있었고, 검토 결과 실제로 타당한 문제였습니다.

## 0. 배경 및 범위

이 앱은 편집 하나가 끝날 때마다 `saveData()`가 **전체 상태를 동기적으로 `JSON.stringify`해서 `localStorage`에 기록**하는 구조입니다. `localStorage`는 보통 5~10MB 남짓의 용량 한도가 있는데, 지도 배경 이미지(스캔한 지도, 그림판/포토샵으로 그린 세계지도 등)는 수백 KB에서 수 MB에 달할 수 있어 이 한도에 금방 부딪힙니다. 게다가 지도 "회차(버전)" 기능은 현재 회차의 내용을 통째로 복제해 새 회차를 만드는데, 배경 이미지 문자열도 그대로 복제되어 회차를 몇 개만 늘려도 저장 용량이 배로 불어났습니다.

해결 방향은 단일 파일·오프라인 우선이라는 이 앱의 기존 아키텍처를 유지하면서(빌드 도구·외부 서버 없이), 큰 바이너리 데이터만 브라우저 네이티브 API인 **IndexedDB**로 옮기는 것입니다. IndexedDB는 별도 설치나 빌드 없이 모든 최신 브라우저에 내장되어 있고 용량 한도가 `localStorage`보다 훨씬 넉넉합니다.

## 1. 데이터 모델

```js
mp.bgImage      // (레거시) 배경 이미지 Base64 문자열 — 새로 저장할 땐 더 이상 안 씀
mp.bgAssetId    // (신규) IndexedDB 자산 저장소의 키
mp.traceImage   // (레거시) 자동 선 감지 결과 Base64
mp.traceAssetId // (신규) IndexedDB 자산 저장소의 키
```

`bgAssetId`/`traceAssetId`가 있으면 그것을 쓰고, 없으면(마이그레이션 전이거나 IndexedDB를 못 쓰는 환경) 예전처럼 `bgImage`/`traceImage` 문자열을 그대로 쓰는 **이중 경로**로 설계했습니다. 완전히 새로운 스키마로 갈아엎지 않고 기존 필드를 안전망으로 남겨둔 것입니다.

핵심 헬퍼(모두 콜백 스타일 — 이 앱의 다른 비동기 코드와 동일한 관례):
- `putMapAsset(dataUrl, callback)` — 새 자산 ID로 저장하고 콜백으로 ID를 돌려줌.
- `getMapAsset(id, callback)` — ID로 데이터를 읽음(한 번 읽으면 세션 메모리 캐시에 유지).
- `releaseMapAssetIfUnused(id)` — 어떤 지도도 더 이상 참조하지 않는 자산만 실제로 삭제(아래 3장 참고).
- `mapHasBgImage(mp)` / `mapHasTraceImage(mp)` — assetId든 레거시 문자열이든 상관없이 "배경 이미지가 있는가"를 판정.
- `resolveMapBgSource(mp, callback)` — 크롭/회전/재추적처럼 원본 픽셀이 실제로 필요한 편집에서 쓰는, assetId/레거시 문자열을 가리지 않는 공용 조회.

## 2. 자산 불변식 — "한 번 쓰이면 내용이 안 바뀐다"

회차(버전)가 같은 배경 이미지를 공유할 수 있어야 하므로(복제 방지), **크롭·회전처럼 이미지 내용이 바뀌는 편집은 기존 자산을 덮어쓰지 않고 항상 새 assetId를 만듭니다.** 이 불변식 덕분에 "다른 회차가 이 자산을 아직 쓰고 있을 수도 있다"는 걱정 없이 안전하게 참조를 공유할 수 있습니다 — 내용이 바뀌는 시점엔 이미 새 ID로 넘어가 있으니까요.

`addMapVersion`(새 회차 만들기)은 이제 `bgAssetId`를 그대로 복사합니다(문자열 복제가 아니라 참조 공유):

```js
bgAssetId: mp.bgAssetId || null, bgImage: mp.bgAssetId ? null : (mp.bgImage || null),
```

## 3. 참조 카운팅 없는 정리(GC)

정확한 참조 카운트를 유지하는 대신, 자산을 지울 수도 있는 시점마다(배경 이미지 교체·삭제, 지도/회차 삭제) **그 시점의 `MAPS` 전체를 훑어 아직 참조하는 지도가 있는지 확인**하고 없을 때만 IndexedDB에서 실제로 지웁니다(`releaseMapAssetIfUnused`). 카운터를 따로 관리하지 않아도 되고, 상태가 어긋날 걱정도 없습니다 — 다소 O(지도 수)지만 지도 개수가 수백 개 규모가 아닌 이상 문제되지 않습니다.

**Undo/Redo는 자산을 정리하지 않습니다.** 실행취소로 되돌아간 뒤 다시실행(redo)이 그 자산을 다시 필요로 할 수 있기 때문입니다. 정리는 오직 확정적인 편집(크롭/회전으로 새 자산 생성, 배경 이미지 삭제, 지도/회차 삭제)에서만 일어납니다.

## 4. 렌더링 — drawMap을 async로 바꾸지 않고 비동기 로드 끼워넣기

`drawMap(mp)`는 편집 하나가 끝날 때마다(그리고 undo/redo, 팬/줌 등에서도 간접적으로) 호출되는, 이 앱에서 가장 자주 불리는 함수 중 하나입니다. 이걸 `async`로 바꾸면 파급 범위가 지도 시스템 전체로 번지므로, 대신 **"캐시에 있으면 동기로 그리고, 없으면 로드를 시작한 뒤 다시 그린다"** 패턴을 썼습니다:

```js
var src = resolveMapBgSrc(mp, mp.bgMode); // 캐시에 있으면 문자열, 없으면 undefined
if (src === undefined) {
  getMapAsset(assetId, function(){ if (currentMap()?.id === mp.id) drawMap(mp); });
  src = null; // 이번 렌더에는 일단 이미지 없이
}
```

첫 렌더는 배경 이미지 없이 나갔다가, IndexedDB 조회가 끝나면(보통 수십 ms) 한 번 더 그려져서 이미지가 나타납니다. 한 번 로드된 자산은 세션 메모리 캐시(`_mapAssetCache`)에 남아 있어서 같은 지도를 여러 번 열어도 다시 로드하지 않습니다.

## 5. 마이그레이션

기존에 `mp.bgImage`/`mp.traceImage`에 문자열이 직접 저장된(예전 형식) 지도는 페이지가 처음 렌더링된 직후 `migrateMapImageAssets()`가 한 번 훑어서 IndexedDB로 옮기고, 성공하면 문자열 필드를 비웁니다(그래야 이후 `saveData()`가 그 큰 문자열을 더 이상 `localStorage`에 다시 쓰지 않습니다). **IndexedDB 저장이 실패하면 문자열 필드를 그대로 남겨** 예전 방식으로 계속 동작하게 했습니다 — 마이그레이션 실패가 이미지 유실로 이어지면 안 되기 때문입니다.

## 6. 저장 공간 표시

사이드바 하단 "데이터 관리"를 펼치면 `localStorage`에 실제로 저장된 크기(진짜 제약 자원)와, 참고용으로 IndexedDB에 있는 지도 이미지 개수·용량을 함께 보여줍니다. `localStorage` 사용량이 커지면(4MB 초과) 지금 내보내기로 백업하라는 경고가 뜹니다. IndexedDB 전체를 커서로 훑어야 해서, 페이지 로드 시가 아니라 이 패널을 펼칠 때만 계산합니다.

## 7. 테스트

- `test_storage_usage_display.js`(2개) — 저장 공간 표시가 계산되어 뜨는지, 이미지 업로드 후 개수·용량이 반영되는지.
