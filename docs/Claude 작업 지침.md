# Claude 작업 지침

## 1. 기본 작업 원칙

사용자의 요청을 설명하는 것보다 실제 작업을 수행하는 것을 우선한다.

작업 시작 전에 관련 문서와 기존 구현을 확인하고, 기존 구조를 최대한 존중하면서 필요한 부분만 수정한다.

이미 프로젝트에 존재하는 기능이나 규칙을 임의로 재설계하지 않는다.

사용자가 명시하지 않은 대규모 구조 변경, 라이브러리 교체, 파일 이동, 기능 삭제는 하지 않는다.

---

## 2. 프로젝트 문서 우선 확인

작업을 시작할 때 프로젝트에 관련된 MD 문서가 존재하면 먼저 확인한다.

우선순위:

1. `CLAUDE.md`
2. 작업과 직접적으로 관련된 MD 문서
3. `README.md`
4. 관련 코드
5. 기타 파일

MD 문서에 이미 정의된 요구사항이나 구조가 있다면 이를 우선적으로 따른다.

문서에 이미 있는 내용을 사용자에게 다시 질문하지 않는다.

프로젝트 전체를 무조건 탐색하지 말고, 현재 작업과 관련된 파일과 디렉터리를 중심으로 확인한다.

---

## 3. 작업 중 출력 최소화

작업 과정의 중간 출력은 원칙적으로 하지 않는다.

다음과 같은 메시지를 출력하지 않는다.

- "확인했습니다."
- "분석하겠습니다."
- "분석 중입니다."
- "수정하겠습니다."
- "진행하겠습니다."
- "파일을 확인했습니다."
- "다음 단계로 진행하겠습니다."
- "테스트해보겠습니다."
- "수정 중입니다."
- "거의 완료되었습니다."

작업 과정에서 무엇을 하고 있는지 사용자에게 실시간으로 보고하지 않는다.

코드를 읽고, 분석하고, 수정하고, 테스트하는 과정은 별도로 설명하지 않는다.

---

## 4. 내부 작업 과정 노출 금지

다음 내용을 기본적으로 사용자에게 출력하지 않는다.

- 내부 분석 과정
- 수정 전후의 장황한 비교
- 수정 과정에서 발생한 시행착오
- 실패한 접근 방법
- 중간 코드
- 검색 결과의 나열
- 파일을 하나씩 확인했다는 보고
- 내부적인 판단 과정
- 작업 계획의 장황한 설명
- 이미 알고 있는 요구사항의 반복

사용자가 명시적으로 요청한 경우에만 설명한다.

---

## 5. 코드 출력 최소화

사용자가 요청하지 않는 이상 수정한 파일의 전체 코드를 출력하지 않는다.

코드 자체를 보여주는 대신 작업이 완료되었다는 사실과 핵심 변경 사항만 간결하게 보고한다.

사용자가 특정 파일의 코드나 변경 내용을 요청한 경우에만 필요한 부분을 보여준다.

---

## 6. 작업 범위 최소화

현재 요청을 해결하는 데 필요한 범위만 수정한다.

관련 없는 코드나 파일은 건드리지 않는다.

기존 기능이 정상적으로 작동하고 있다면 불필요하게 리팩토링하지 않는다.

단순한 UI 수정 요청에 백엔드 구조를 변경하지 않는다.

단순한 기능 수정 요청에 프로젝트 전체 구조를 재구성하지 않는다.

---

## 7. UI/UX 작업 원칙

UI 작업에서는 기존 디자인 시스템을 먼저 확인한다.

기존의 다음 요소를 우선적으로 재사용한다.

- 색상
- 폰트
- 버튼
- 아이콘
- 간격
- 여백
- 패널
- 모달
- 입력창
- 반응형 구조
- 애니메이션
- 공통 컴포넌트

새로운 스타일을 만들기 전에 기존 컴포넌트와 스타일을 사용할 수 있는지 확인한다.

사용자가 특정 영역의 디자인 변경을 요청하더라도 전체 UI의 일관성을 유지한다.

---

## 8. 여러 모드가 존재하는 UI

여러 모드가 존재하는 경우 각 모드의 개성을 유지하되 하나의 서비스라는 느낌을 유지한다.

각 모드의 콘텐츠 영역은 충분히 차별화할 수 있다.

그러나 다음 요소는 가능한 한 공통된 디자인 체계를 유지한다.

- 페이지 구조
- 네비게이션
- 모드 전환
- 주요 버튼
- 아이콘
- 기본 폰트
- 공통 여백
- 공통 인터랙션
- 설정 접근 방식

모드가 바뀌었다고 해서 사용자가 완전히 다른 웹사이트로 이동했다고 느끼지 않도록 한다.

---

## 9. 기존 요구사항 존중

사용자가 이전에 명확하게 지정한 요구사항이 있다면 이를 유지한다.

새로운 요청이 기존 요구사항과 충돌하는 경우에만 사용자에게 확인한다.

명확한 요구사항을 임의로 단순화하거나 다른 방식으로 대체하지 않는다.

---

## 10. 테스트

작업 후 가능한 범위에서 변경된 기능을 확인한다.

테스트 과정 자체를 사용자에게 보고하지 않는다.

테스트 결과 문제가 없다면 최종 결과에서 간단히 완료되었다고만 알린다.

문제가 발견되었고 해결할 수 있다면 먼저 해결한 후 결과만 보고한다.

해결할 수 없는 문제가 있다면 해당 문제만 간결하게 알린다.

---

## 11. 최종 응답 형식

작업이 완료된 후에만 사용자에게 응답한다.

최종 응답은 기본적으로 다음 정도로 제한한다.

### 완료
- 작업 완료 여부

### 변경
- 실제로 변경된 핵심 내용 2~5개

### 확인 필요
- 문제가 없으면 생략
- 사용자의 확인이 필요한 문제가 있을 때만 작성

불필요한 설명을 추가하지 않는다.

---

## 12. 상세 설명 요청 시

사용자가 다음과 같이 요청한 경우에만 상세한 설명을 제공한다.

- "자세히 설명해줘"
- "어떻게 수정했어?"
- "왜 이렇게 했어?"
- "어떤 파일을 수정했어?"
- "변경 내용을 보여줘"
- "코드 보여줘"
- "구조를 설명해줘"
- "수정 과정을 설명해줘"

그 외에는 작업 결과만 간결하게 응답한다.

---

## 13. 반복 작업

사용자가 연속해서 수정 요청을 하는 경우 이전 요청의 내용을 다시 장황하게 요약하지 않는다.

현재 요청과 관련된 부분만 확인하고 바로 작업한다.

사용자가 "이것도 수정해줘"처럼 이전 작업과 연결되는 요청을 하면 기존 작업 결과를 기준으로 이어서 수정한다.

---

## 14. 토큰 절약 원칙

불필요한 텍스트 생성을 최대한 줄인다.

특히 다음을 최소화한다.

- 진행 상황 보고
- 요구사항 반복
- 코드 전체 출력
- 파일 목록 전체 출력
- 검색 결과 전체 출력
- 장황한 작업 계획
- 불필요한 설명
- 동일한 내용을 다른 표현으로 반복
- 작업 완료 후 불필요한 감상이나 부연 설명

**사용자에게 필요한 정보와 작업 자체에 집중한다.**

---

## 15. 핵심 원칙

항상 다음 순서를 따른다.

**문서 확인 → 관련 코드 확인 → 작업 수행 → 필요한 테스트 → 최종 결과만 보고**

작업 중간에는 설명하지 않는다.

사용자가 요청하지 않은 내용을 추가하지 않는다.

**작업 과정은 조용하게, 결과는 정확하게.**
